1. Introducción

El proyecto Mike API es un backend en FastAPI para un refrigerador inteligente: gestiona usuarios, refrigeradores, alimentos, tickets de compra, imágenes, sensores y cámaras, con persistencia en PostgreSQL y archivos en MinIO. Capturar a mano cada producto comprado es lento y propenso a errores, así que esta actividad automatiza el registro: un agente de IA lee la foto de un ticket, interpreta su contenido y llena las APIs con los datos y las imágenes correspondientes.

Para que el agente pueda actuar sobre el sistema se construyó un servidor MCP (Model Context Protocol) con la librería FastMCP. Este servidor expone herramientas bien definidas que encapsulan la autenticación JWT, las llamadas HTTP a la API y la subida de archivos a MinIO, un almacenamiento de objetos compatible con Amazon S3.

Objetivos:

  • Exponer las APIs de tickets, alimentos e imágenes como herramientas MCP reutilizables por cualquier agente.
  • Guardar las imágenes de los tickets y de los productos en MinIO y referenciarlas desde la base de datos.
  • Hacer que el agente procese tickets de prueba de principio a fin, sin capturar datos a mano.

2. Desarrollo

2.1 Arquitectura

El agente nunca habla directamente con la base de datos ni con MinIO: todo pasa por las herramientas del servidor MCP. El servidor inicia sesión en la API con un usuario de servicio (MCP_API_USER en .env), renueva el token si expira y usa boto3 para subir archivos al bucket fastapi-images.

2.2 Infraestructura

  • PostgreSQL 15 y MinIO levantados con docker compose up -d (puertos 5433, 9000 y 9001).
  • API FastAPI con uvicorn main:app --port 8000; rutas bajo /api/v1.
  • Entorno virtual de Python 3.14 con fastmcp 4.1, boto3, httpx y Pillow.

Ejemplo de herramienta: FastMCP genera el esquema de entrada a partir de los type hints y el docstring se convierte en la descripción que lee el agente.

@mcp.tool
def registrar_ticket(
    refrigerator_id: int,
    image_path: str,
    store_name: str,
    purchase_date: date,
    raw_text: str,
) -> dict[str, Any]:
    """Sube la imagen del ticket a MinIO y crea el PurchaseTicket en la API.

    image_path: nombre del archivo dentro de tickets/ (ej. 'ticket_soriana.png').
    raw_text: texto transcrito del ticket (productos, precios, total).
    """
    url = _upload(image_path, "tickets")
    return api.request("POST", "/purchase-tickets/", json={
        "user_id": api.user_id,
        "refrigerator_id": refrigerator_id,
        "store_name": store_name,
        "purchase_date": purchase_date.isoformat(),
        "ticket_image_url": url,
        "raw_text": f"archivo: {Path(image_path).name}\n{raw_text}",
        "processed_at": False,
    })

El servidor se registra para el agente en .mcp.json, así Claude Code lo carga automáticamente al abrir el proyecto.

Con tickets/generar_tickets.py (Pillow) se generaron tres tickets falsos de tiendas distintas y doce fotos ilustrativas de productos.

2.5 El agente

El agente es Claude conectado al servidor MCP. Las instrucciones están en agente/prompt.md:

  1. Consulta los tickets pendientes y obtiene el refrigerador.
  2. Abre cada imagen y extrae, con visión, la tienda, la fecha y los productos con cantidad, unidad e importe.
  3. Normaliza los datos: nombre legible, categoría, unidad (kg, L o pz) y la fecha en formato ISO.
  4. Como los tickets no traen fecha de caducidad, la estima con la vida útil típica de cada producto.
  5. Registra el ticket, cada alimento con sus imágenes, y marca el ticket como procesado.

Se ejecuta con agente\run_agente.ps1 (Claude Code en modo headless con --mcp-config .mcp.json). La sesión ejecutada también quedó como script reproducible en agente/sesion_agente.py, y cada llamada a herramienta con su respuesta se registró en agente/ejecucion_agente.log. Extracto:

3. Conclusión

La integración cumplió su objetivo: a partir de tres imágenes de tickets, el agente registró de forma autónoma 3 tickets, 12 alimentos y 24 imágenes de alimentos. Además, guardó 15 archivos en MinIO: los 3 tickets y las 12 fotos de productos. Nadie tuvo que capturar datos a mano: el agente interpretó texto no estructurado, lo normalizó y decidió qué herramienta usar en cada paso.

El servidor MCP fue la pieza clave: separa la lógica de negocio y las credenciales del modelo de IA. El agente solo conoce herramientas con nombres, parámetros tipados y descripciones claras, mientras que la autenticación JWT, las URLs y el acceso a MinIO quedan del lado del servidor. Esto hace al sistema más seguro y fácil de mantener. Además, el mismo servidor puede usarse con otros clientes compatibles con MCP.

Mejoras posibles: leer la fecha de caducidad desde fotos de las etiquetas; agregar un endpoint de subida de imágenes a la API para no acceder a MinIO desde el servidor MCP; usar URLs firmadas para mostrar las imágenes al cliente; y procesar tickets reales automáticamente cuando se suban desde la app o desde la cámara del ESP32.
